# Orchestrator Service

FastAPI service for the AI chat POC. It defines the public request/response
contract, request identity model, structured JSON logging shape, and error
handling that future agent, MCP, and telemetry work should build on.

`POST /chat` is wired to a deterministic LangGraph orchestrator
(`app/orchestrator/`): keyword-based routing dispatches to a DB Agent and/or
a REST API Agent (currently stubs — see `app/agents/`), threading the four
correlation IDs through every node and emitting structured `agent.*` log
events along the way.

## Running Locally

Requires Python 3.11+.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python -m app.main
```

`python -m app.main` starts uvicorn through the `__main__` block in
`app/main.py`, so `HOST`, `PORT`, `APP_ENV`, and `LOG_LEVEL` from `.env` are
used directly. With the default `APP_ENV=development`, uvicorn reloads on code
changes.

## Endpoints

### `GET /health`

Returns:

```json
{ "status": "ok" }
```

`/health` intentionally has no downstream dependencies and bypasses request
context/logging middleware, so frequent liveness checks do not generate fake
request IDs.

### `POST /chat`

Request body:

```json
{
  "message": "hello",
  "session_id": "optional-caller-supplied-id",
  "tenant_id": "optional-caller-supplied-id"
}
```

Success response:

```json
{
  "reply": "...",
  "run_id": "...",
  "request_id": "...",
  "session_id": "...",
  "tenant_id": "..."
}
```

`reply` is assembled by the orchestrator graph from whichever sub-agent(s)
handled the message — not a fixed echo string.

Only `message` is required. `session_id` and `tenant_id` can be provided by
the caller. `run_id` and `request_id` are always generated by the service and
ignored if the caller sends them.

Validation and error responses also include the same four identifiers whenever
request context middleware runs.

## Manual Checks

```bash
curl http://localhost:8001/health

curl -X POST http://localhost:8001/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "hello"}'

curl -X POST http://localhost:8001/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "hello", "session_id": "demo-session"}'

curl -X POST http://localhost:8001/chat \
  -H "Content-Type: application/json" \
  -d '{}'
```

## Running Tests

```bash
python -m pytest
```

Tests live in `tests/` and cover health checks, chat responses, ID handling,
validation paths, oversized bodies, and log redaction expectations. No running
server is required; FastAPI is exercised in-process with `TestClient`.

## Request Identity

Every non-health, non-`OPTIONS` request gets a `RequestContext` with:

| ID | Caller-suppliable? | Purpose |
| --- | --- | --- |
| `run_id` | No | Business-level correlation ID for one end-to-end request. |
| `request_id` | No | Per-HTTP-request identifier. |
| `session_id` | Yes | Groups turns in a conversation. |
| `tenant_id` | Yes | Tenant grouping value; currently unauthenticated. |

Callers should resend the same `session_id` for each turn in a conversation.
If omitted, the service generates a new session ID, so downstream telemetry
will treat the request as a new conversation.

## Logging Contract

`app/logging_utils.py` writes one JSON object per log line to stdout. Request
logs include:

- `timestamp`
- `service.name`
- `event`
- `run_id`
- `request_id`
- `session_id`
- `tenant_id`
- `endpoint`, `status_code`, and other event-specific metadata when present

Raw user message content is intentionally not logged. The current
`service.name` value is `backend-api`; keep that in mind if dashboards or
queries start referring to the orchestrator service by a different product
name.

## Configuration

Configured through environment variables or `.env`:

- `APP_ENV` - `development` enables uvicorn reload.
- `HOST` - bind host, default `127.0.0.1` locally.
- `PORT` - bind port, default `8001`.
- `LOG_LEVEL` - Python logging level.
- `MODEL_API_KEY` - reserved for future model integration.
- `DEFAULT_TENANT_ID` - fallback tenant when request body omits `tenant_id`.
- `CORS_ALLOWED_ORIGINS` - comma-separated origins or `*`.

## Known Limitations

- DB Agent and REST API Agent (`app/agents/`) are stubs: they simulate a
  successful result and never call an LLM, MCP, or a real tool yet.
- The shared retry helper (`call_tool_with_retry`) and the `agent.tool_selected`
  / `agent.tool_returned` / `agent.retried` / `agent.llm_call` events described
  in the design docs aren't implemented yet — there's no MCP call for them to
  wrap until the real agents land.
- The orchestrator uses abort-on-first-failure: any step failure marks the
  whole run failed and skips every remaining step, even ones that are
  logically independent of the failure (e.g. a later document-search step
  unrelated to an earlier failed order lookup). This is a **deliberate POC
  simplification**, not a partially-built feature — a "continue past an
  independent failure and assemble a partial-result answer" path does not
  exist and is not planned for this phase. If a future phase needs
  per-step-independent failure handling, that is new scope, not a bug fix.
- Routing keywords (`app/orchestrator/routing.py`) include some common
  English words — `"status"`, `"carrier"`, `"order"`, `"document"` — that
  will misroute real, unscripted traffic with high confidence and no
  fallback signal: e.g. "what's the status of the deployment pipeline" or
  "carrier pigeons are fascinating" both match a rule and get dispatched to
  a real agent as if genuinely on-topic. This is **not a matching bug** —
  word-boundary matching (`_KEYWORD_PATTERNS`) is working correctly, and
  none of these are accidental substring matches. It's a keyword-choice/
  scope limitation: these words are simply common enough that whole-word
  matching alone can't distinguish an on-topic use from an unrelated one.
  Accepted for the POC's scripted/rehearsed demo use case, exactly like the
  abort-on-first-failure simplification above — not an oversight. If a
  future phase routes real, unscripted user traffic, this keyword list
  needs tightening (or routing needs a confidence/context signal beyond
  bare keyword presence) before then.
- `tenant_id` is trusted as caller input and has no authentication or authorization yet.
- `/health` only proves the process is alive; it does not check downstream readiness.
- No real OTel SDK/collector integration is wired into this service yet.
- CORS defaults to `*`; set `CORS_ALLOWED_ORIGINS` before using this outside the demo/dev environment.
- **Open decision — `service.name` naming discrepancy:** this codebase emits
  `service.name: "backend-api"` on every log line (see
  `app/logging_utils.py`'s `SERVICE_NAME`), and the orchestrator/routing
  implementation spec is aligned to that value. However, the OTel design
  doc's own example agent-semantic event uses
  `service.name: "agent-orchestrator"` instead. This is a real, unresolved
  naming discrepancy between the two governing documents — not a bug in
  this code. It needs to be resolved with whoever owns the
  monitoring/dashboard side before they build queries or dashboards against
  one name or the other; changing it silently later would break any
  dashboard already querying on `"backend-api"`.
- **Open decision — event-name vocabulary mismatch between the two governing
  documents:** the "Multi-Agent Client Architecture" spec (which this
  implementation follows) and the actual code use `agent.step_started`,
  `agent.step_completed`, `agent.step_failed`, `agent.tool_selected`,
  `agent.tool_returned`, `agent.retried`. The original "OTel POC Design"
  architecture document's own "Standard event types" list uses a different
  vocabulary for the same concepts: `agent.planner.step`, `agent.selected`,
  `agent.tool.selected`, `agent.tool.result`, `agent.retry` (singular),
  `agent.completed`, `agent.error` — none of these string-match what's
  actually implemented. This is not a code defect — the implementation
  correctly follows the more detailed, aligned spec — but it means the two
  governing documents describe two different event vocabularies for the same
  concepts. Whoever wires the real OTel/monitoring layer needs one canonical,
  agreed event vocabulary before building dashboards or queries, not two
  partially-overlapping documents. This needs a team decision, not a code
  fix.
- Related to the above: this same class of problem affects the OTel doc's
  own example event schema, which uses `"event.type"` as the field key and
  includes `trace_id`/`span_id`, while the implemented schema uses `"event"`
  as the key and correctly omits `trace_id`/`span_id` (per the "reserved for
  future OTel SDK wiring" decision already documented above). This is a
  discrepancy in the OTel document's own example, not a code defect, but
  worth resolving in the same team conversation as the event-name vocabulary
  mismatch above, since both stem from the two documents not being fully
  reconciled with each other.
