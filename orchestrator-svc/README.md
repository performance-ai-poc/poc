# Performance AI — Backend

Minimal FastAPI skeleton for the Performance AI agent system. It defines the
request/response contract and request-identity plumbing that everything
else — a LangGraph orchestrator, the agents themselves, an MCP server, and an
OpenTelemetry instrumentation layer — will be built on top of. **There is no
real agent logic yet**: `/chat` returns a placeholder echo so the contract
can be exercised end-to-end before anything downstream exists.

## What's next

This is deliberately a skeleton, not a finished service. The intended next
steps are:

- Replace `app/service.py`'s `generate_reply` with a call into a LangGraph
  orchestrator that fans out to real agents.
- Add an MCP server as a tool/data source the orchestrator calls into.
- Point an OpenTelemetry layer at the structured JSON logs this service
  already emits (every log line carries `run_id`, `request_id`,
  `session_id`, `tenant_id`) — no changes needed here for that to work.
- Add a redaction layer before any raw message content is persisted anywhere
  beyond the single response round-trip.

## Running locally

Requires Python 3.11+.

```powershell
cd backend
py -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
python -m app.main
```

`python -m app.main` starts uvicorn programmatically (see the `__main__`
block at the bottom of `app/main.py`), reading `HOST`, `PORT`, `APP_ENV`, and
`LOG_LEVEL` from `.env` via `app/config.py`. Change `PORT` in `.env` and it
takes effect on the next run — there's no separate `--port` flag to remember
to keep in sync. With the default `APP_ENV=development`, the server
auto-reloads on code changes, same as `uvicorn --reload` used to.

`.env` is git-ignored — copy the example rather than editing it in place.

## The contract

### `GET /health`

Always returns `200` and never depends on anything else in the process
(no DB, no telemetry backend). Used for standard container/load-balancer
health checks. It also bypasses `RequestContextMiddleware` entirely (see
`app/middleware.py`'s `_skips_context`), so it never mints IDs or emits
`api.request.*` log lines — safe to poll at Kubernetes liveness-probe
frequency without polluting the structured log stream.

```json
{ "status": "ok" }
```

### `POST /chat`

Request body:

```json
{
  "message": "hello",
  "session_id": "optional-caller-supplied-uuid",
  "tenant_id": "optional-caller-supplied-uuid"
}
```

Only `message` is required. `session_id` and `tenant_id` may each be
omitted; the server generates a UUID4 for whichever one is missing.

`run_id` and `request_id` are **not** accepted as input at all — they are
always generated by the server, on every request, regardless of what a
caller sends. If a caller includes `run_id` or `request_id` in the request
body anyway, those values are silently ignored (not rejected — the request
still succeeds); only `message`, `session_id`, and `tenant_id` are read from
the body. See "Who controls which ID" below for why.

Success response (`200`):

```json
{
  "reply": "Received: hello",
  "run_id": "…",
  "request_id": "…",
  "session_id": "…",
  "tenant_id": "…"
}
```

Error response (`422` — missing/invalid body, `500` — unexpected failure):

```json
{
  "error": "invalid_request",
  "detail": "The request body is malformed or missing required fields (e.g. 'message').",
  "run_id": "…",
  "request_id": "…",
  "session_id": "…",
  "tenant_id": "…"
}
```

The same four identifiers appear on every response — success or error —
because they are resolved by middleware before the request body is even
validated.

### Who controls which ID

| ID | Caller-suppliable? | Notes |
| --- | --- | --- |
| `run_id` | **No** — always server-generated | See below. |
| `request_id` | **No** — always server-generated | See below. |
| `session_id` | Yes | Reuse across a conversation — see "Important: session continuity" below. |
| `tenant_id` | Yes, currently unverified | See "Known POC limitation: tenant_id" below. |

**`run_id` and `request_id` are always server-generated.** Nothing in the
design requires a caller to control either of these, and letting a caller
set them was a real risk: a buggy or malicious client could reuse the same
`run_id` across unrelated conversations, incorrectly merging them together
once correlation/analytics exist downstream. `app/middleware.py`'s
`RequestContextMiddleware` mints both fresh on every request and never reads
them from the caller's body — see `app/schemas.py`, which doesn't even accept
them as `ChatRequest` fields.

**`run_id` vs. a future `trace_id`**: `run_id` is our own business-level
correlation ID for "this one end-to-end request" — a server-generated UUID4.
It is deliberately *not* a W3C `trace_id`. Once LangGraph/OTel
instrumentation is wired in, the OTel SDK will mint real `trace_id`/`span_id`
values per span, and `run_id` will be attached to those spans as a
correlation attribute rather than replaced by them. This matches the
architecture doc's design, which treats a stable request/run ID and W3C
trace context as two separate, valid correlation mechanisms.

### Fixed: CORS preflight and `/health` logging noise

`RequestContextMiddleware` used to run on every request, including CORS
preflight (`OPTIONS`) requests and `/health` polls, so each one produced full
`api.request.started`/`api.request.completed` log lines with freshly-minted
`run_id`/`request_id`/`session_id`/`tenant_id` values — indistinguishable
from real traffic once a shared log-based telemetry pipeline exists. This is
now fixed: `RequestContextMiddleware` returns immediately for any `OPTIONS`
request or a request to `/health` (see `_skips_context` in
`app/middleware.py`), before any ID resolution or logging happens. Both
still respond normally — `/health` returns its usual `200`, and CORS
preflight still gets correct headers from `CORSMiddleware` further down the
stack — they just no longer appear in the structured log stream.

### Important: session continuity

To keep a multi-turn conversation grouped together, the caller (frontend)
must resend the same `session_id` on every subsequent `/chat` call in that
conversation — take it from the first response and pass it back on every
following request. If `session_id` is omitted, the backend generates a fresh
random one for that request, so each request will look like an unrelated,
brand-new session in the logs and any future telemetry. This matters once
multi-turn memory (via the upcoming LangGraph orchestrator) is wired in:
without consistent `session_id` reuse, conversation history/context won't be
grouped correctly.

```json
// First request — no session_id supplied
{ "message": "hello" }

// First response — note the generated session_id
{ "reply": "…", "session_id": "48fdeeab-f0a6-4438-8fa5-a2327dc04726", "...": "..." }

// Second request in the same conversation — reuse that session_id
{ "message": "what did I just say?", "session_id": "48fdeeab-f0a6-4438-8fa5-a2327dc04726" }
```

## Running tests

Automated tests live in `tests/` and cover the `/health` and `/chat`
contract (valid requests, ID handling, and the 422/413 error paths). With
dependencies installed (`pip install -r requirements.txt`, which includes
`pytest` and `httpx`):

```bash
python -m pytest
```

Run from the `backend/` directory — `pytest.ini` puts it on `sys.path` so
`from app.main import app` resolves regardless of how pytest is invoked. No
running server is needed; tests exercise the app in-process via FastAPI's
`TestClient`.


## How the four IDs flow through the code

1. `app/middleware.py`'s `RequestContextMiddleware` runs first for every
   request, except `/health` and any `OPTIONS` (CORS preflight) request,
   which bypass it entirely — see "Fixed: CORS preflight and `/health`
   logging noise" above. For everything else, it best-effort peeks the raw
   JSON body for `session_id` and `tenant_id` only — `run_id` and
   `request_id` are never read from the body, and are always freshly
   generated. Anything missing (`session_id`,
   `tenant_id`, and always `run_id`/`request_id`) is filled in via
   `app/context.py`'s `resolve_context` (UUID4 generation), and the
   resulting `RequestContext` is stored on `request.state.context`. This
   happens *before* FastAPI validates the body against `ChatRequest`, so
   even a malformed request gets a fully-formed context.
2. Every route handler and exception handler pulls that context back out
   (`_context_from_request` in `app/main.py`) and passes it as an explicit
   argument to internal functions — see `generate_reply(message, ctx)` in
   `app/service.py`. Nothing relies on implicit thread-local/contextvar
   state for business logic; the context is a normal function argument.
3. `app/logging_utils.py`'s `log_event(ctx, event, ...)` requires a context
   as its first argument, so it's structurally impossible to emit a
   request-related log line without the four IDs attached. Every log line
   is one JSON object with `run_id`, `request_id`, `session_id`,
   `tenant_id`, `endpoint`, `timestamp`, and (where applicable)
   `status_code`.
4. The same context is spread into every JSON response — success or
   error — via `**ctx.as_dict()`.

## Design notes

- **Fail-open logging**: `app/logging_utils.py` only ever writes to stdout.
  Nothing in the request path makes a synchronous call to an external
  telemetry/logging backend, so a down collector can never block or fail a
  request.
- **Metadata-only by default**: log lines never include the raw `message`
  body — only the four identifiers, endpoint, timestamp, and status. This
  keeps the skeleton safe to point at a shared log aggregator before a
  redaction layer exists.
- **No hardcoded config**: everything configurable (`HOST`, `PORT`,
  `LOG_LEVEL`, `APP_ENV`, and a placeholder `MODEL_API_KEY` for later) is
  read via `app/config.py` (`pydantic-settings`) from environment variables /
  `.env`, and actually consumed by the `__main__` entrypoint in
  `app/main.py` (and by the Dockerfile's `CMD`) — not just defined and
  ignored.
- **`service.name` on every log line**: `app/logging_utils.py` stamps
  `service.name: "backend-api"` on every structured log line, so that once
  the orchestrator, agents, and MCP server are logging in the same shape,
  records can be told apart by which service emitted them.
- **`api.*`-namespaced event names**: this service's own log events (e.g.
  `api.request.started`, `api.service.generate_reply.start`) are prefixed
  with `api.` to keep them distinct from the `agent.*`/`mcp.*` semantic
  event names the architecture doc defines for the future orchestrator/agent
  layer — the two are related but not the same kind of event.

## Open Decisions & Known Limitations

Deferred decisions and known gaps in the backend so far, consolidated here
so they don't need to be rediscovered later:

- **`tenant_id` has no authentication.** Any caller can claim any
  `tenant_id` string in the request body (see `ChatRequest.tenant_id` in
  `app/schemas.py`), and it's trusted as-is. This is an intentional
  POC-stage simplification: the architecture doc classifies cross-tenant
  isolation as a **Production**-class requirement, not **MVP** (§8,
  acceptance criteria table). **Important:** if Agent 2's mock data or the
  MCP server end up organized per-tenant, this stops being a harmless
  simplification and becomes a real access-control gap — flag this
  explicitly to whoever defines Agent 2's data/scope before that work
  starts.

- **The `tenant_id` fallback is now a stable default, not a random UUID —
  but it's still unauthenticated.** `app/config.py`'s `default_tenant_id`
  (env `DEFAULT_TENANT_ID`, default `"default-tenant"`) is used whenever a
  caller omits `tenant_id`, so anonymous/demo traffic groups under one
  consistent tenant instead of each request becoming its own one-off
  tenant. This fixes correlation, but it does not add authentication: a
  caller can still claim any `tenant_id` string, including this default's
  own value — see the `tenant_id` limitation note directly above.

- **`run_id` vs. LangGraph's own run/thread identity is not yet decided.**
  `app/context.py` mints `run_id` as a plain UUID4 per HTTP request, but
  LangGraph has its own `run_id`/`thread_id` concepts in `RunnableConfig`.
  Before wiring the orchestrator (step 4), decide explicitly: does our
  existing `ctx.run_id` get passed into LangGraph's invoke config (e.g. as
  `thread_id`, alongside `session_id`), or does LangGraph mint its own
  identity and our `run_id` stay a separate, backend-level correlation ID
  only? This affects how cleanly agent-semantic telemetry correlates back
  to this API layer later.

- **`/health` only checks that the process is running.** It has no real
  dependencies to verify yet (see "Fixed: CORS preflight and `/health`
  logging noise" above), which is correct for today. Once the model API,
  MCP server, and orchestrator exist (later steps), decide explicitly
  whether `/health` should reflect deeper readiness — e.g. can this
  instance actually serve a request — while keeping it independent
  specifically of the telemetry Collector, per the architecture doc's
  fail-open contract. Don't let this happen implicitly; a probe that
  silently starts depending on the model API or MCP server changes what a
  "200 OK" means for anyone relying on it.

- **`MODEL_ALIAS` doesn't exist yet — add it before real model
  integration, separate from `MODEL_API_KEY`.** The architecture doc
  requires telemetry events to reference an approved model *alias* (e.g.
  `"approved-model-alias"`), never the literal API key. When step 8 (model
  integration) lands, add a distinct `MODEL_ALIAS` config field in
  `app/config.py` so there's an obviously-correct value to put in a
  telemetry attribute, rather than anyone being tempted to reach for
  `MODEL_API_KEY`.

- **No per-chunk timeout on request body reads.**
  `RequestContextMiddleware._read_body_capped` enforces a byte-count cap but
  has no timeout on how long a client can take to send those bytes — a
  client that drip-feeds data just under the 100KB limit could hold a
  worker open indefinitely. Deferred as a reasonable POC-stage scope-cut,
  not fixed.

- **Logging field naming doesn't yet follow OTel semantic conventions.**
  `app/logging_utils.py` uses ad hoc names like `endpoint` where OTel's HTTP
  semantic conventions would use `http.route`/`url.path`. Not worth changing
  now; worth a pass once real OTel auto-instrumentation is added, to avoid
  field-naming collisions between manual log fields and auto-instrumented
  span attributes.

- **CORS default ships wide open even in "production" mode.** The
  `Dockerfile` sets `APP_ENV=production` but does not set
  `CORS_ALLOWED_ORIGINS`, so the container currently defaults to allowing
  all origins (`*`) regardless of `APP_ENV`. This is fine for the one-week
  demo, but note it explicitly so it doesn't silently ship wide-open to
  whatever real environment this eventually runs in —
  `CORS_ALLOWED_ORIGINS` should be explicitly set to a real, restricted
  origin list before this goes anywhere beyond the demo.

- **Coding rule: never put raw user/prompt content inside an exception's
  message string.** The global exception handler logs the full exception
  message and traceback locally, which is safe today because nothing
  currently throws an error containing raw user content. However, the
  design doc's own passive-telemetry plane treats stdout/stderr as a
  source the OTel Collector scrapes directly once it's deployed (step 3)
  — there is no code-side redaction layer between this service's logs and
  the Collector; redaction is a Collector-side responsibility per the
  doc. This means once real agent/model/tool code exists (steps 6-9), it
  would be very easy for someone to accidentally write something like
  `raise ValueError(f"Model call failed for input: {message}")`, which
  would leak the raw user message straight into a log line the Collector
  picks up by default. State this explicitly as a coding rule for whoever
  builds agent/model/tool wrapper code going forward: never embed raw
  user/prompt/tool content inside an exception's message string. Keep
  that content in local variables only; when logging or raising errors,
  reference identifiers, field names, or error types — never the actual
  content. This is cheap to follow now and expensive to retrofit once
  multiple people are independently writing agent/tool code.
