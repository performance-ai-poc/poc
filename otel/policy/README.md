# Capture policy

Phase 3 (`otel/docs/OTEL_PLAN.md` / `otel/BUILD_PROMPT.md`). Controls whether
`gen_ai.input.messages` / `gen_ai.output.messages` are allowed to reach the
telemetry backend. Nothing else is gated by this layer — every other
redaction rule in `collector-config.yaml`'s `attributes/privacy` processor
(auth headers, cookies, API keys, hashed user/session identifiers,
`gen_ai.system_instructions`) applies unconditionally regardless of policy.

## Files

| File | Purpose |
|---|---|
| `policy.schema.json` | The shape a policy file must match. Documentation/config-review tooling — the Collector never reads this file directly. |
| `metadata-only.yaml` | Default. Current behavior exactly: the two content attributes are deleted before export. |
| `content-approved.yaml` | Permits the two content attributes through. |
| `apply.sh` | Reads `captureMode` out of one of the two files above and applies it. |
| `.env.active` | Generated by `apply.sh`, gitignored (matches the repo's existing `.env.*` ignore rule). Not source — do not hand-edit; re-run `apply.sh` instead. |

## How switching actually works — and its one honest limitation

`apply.sh <mode>` renders the selected file's `captureMode` into a
`CAPTURE_MODE` environment variable, then runs
`docker compose ... up -d --force-recreate otel-collector` — recreating
**only** the Collector container.

This is not a true zero-downtime hot-reload. `collector-config.yaml`'s
`transform/limits` processor reads `${env:CAPTURE_MODE}` via the Collector's
config loader, which resolves environment-variable references once, when the
Collector process starts — not per-record, not on a file-watch. Changing the
env var for an already-running process does nothing; the only way to make a
new value take effect is to start a new process with it, hence the
`--force-recreate`.

**What this does not do:** restart, redeploy, or otherwise touch
`orchestrator-svc`, `mcp-server`, or either UI. Acceptance A9
(`otel/docs/ACCEPTANCE.md`) requires "no application restart" — it does not
require the Collector itself to avoid restarting, and a Collector restart is
explicitly tolerated by C2 (`otel/docs/CONSTRAINTS.md`): "stopping the
Collector produces a telemetry gap, never a failed request." The gap here is
on the order of the container's own start-up time (a few seconds), during
which stdout logging on both services continues completely unaffected.

A genuinely dynamic, no-Collector-restart mechanism would need something like
an OpAMP-managed remote config channel, which is out of scope for this POC —
noted here rather than silently building a lesser version of A9 and calling
it the real thing.

## Why the gate exists before anything emits content

No application code emits `gen_ai.input.messages` / `gen_ai.output.messages`
today (`otel/docs/SEMCONV.md` section 7) — `otel/tests/test_policy_switch.sh`
verifies the gate itself with hand-crafted spans carrying those attributes
directly, the same technique `test_collector_up.sh` and `test_redaction.sh`
use, rather than depending on the orchestrator team's handoff (`otel/HANDOFF.md`)
landing first.
